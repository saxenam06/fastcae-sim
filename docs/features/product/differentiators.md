# What the agentic era makes possible: zenryx's differentiators

Product ideas that optimisation, DOEs and fixed workflows cannot deliver, each with the evidence that prompted it. They are proposals, not plans: one is built only when it earns a PBI on a feature's page. fastcae's earlier list is at `../fastcae/docs/features/product/differentiators.md` (frozen).

**Updated:** 2026-10-13 04:36 by Claude

| Idea | Why only an agent loop can do it | Where it came from |
|---|---|---|
| **A design grown by a chain of optimisations, each in the features the agent read from the last.** A free run shows where the material wants to go; the agent reads its patterns and a concept (how each mount is carried, how each bore is held) and offers the next optimisation production's features to place and size; each step adds manufacturing-grade features and rules; several concepts run side by side and are compared on FE. | A human between two optimisations reads once and loses performance; commercial pattern constraints (symmetry, cyclic patterns, a draw direction) are set by a person before the run. Only a loop can read each result, choose the next constraints from it, and do it for several concepts in an hour. | The engineer, 11 October 18:24 (LOP-24; [the chained optimisation](2026-10-11-chained-optimisation.md)) |
| **The interpretation step, done many times overnight.** A topology field read into several recipes, each a hypothesis with its reason; every reading built under the casting and clean-rib rules, judged by FE, and compared at equal mass against the optimisation's own bound. The interpretation penalty is recorded each time. | In every study read, the steps between the field and the proven CAD are manual and done once or twice (Slavov & Konsulova-Bakalova 2019: 28.65 % promised, 7.33 % delivered). A loop keeps the reason and the result of each reading as data. | LOP-16; [topology optimisation in practice](../../research/2026-10-09-topology-optimisation-in-practice.md), "where this goes beyond practice" |
| **A rib ledger.** Every rib carries its measured reason: its load path, its gain per gram, and the rule that admitted it. Ribs that do not pay are removed, with the record of why. | Templates and one-off optimisations leave ribs nobody can justify. The agent can afford to take each one out, re-solve, and keep the answer. | The engineer, 21:45: "how do we know what are actually required" |
| **A reference picture read into a recipe.** A photograph of a production housing, read by a vision model into the generator's vocabulary, its dimensions always from the contract. | A style becomes a starting hypothesis, not a hand-built preset. | LOP-13; [every style, fitted to the requirement](../../research/2026-10-09-every-style-fitted-to-the-requirement.md) |
| **Features written by the agent, admitted by tests.** A new feature type written as code against the feature API, admitted only by its tests, the castability check and a running FE. | The vocabulary grows with the problems met, not with a vendor's release. | LOP-14 |
| **Every refusal names its rule.** A rib, a reading or a design refused says which rule and where, so the next attempt is aimed. | The record of what failed and why becomes training data for the agent, not noise. | LOP-15 (`ribrules.py`'s refusals in each design's record) |
| **The optimiser's claims audited before they are believed.** Every optimisation's number is checked by other judges before anything is drawn from it: the field as metal or air, the field eroded and dilated, the drawn CAD put back into the optimiser's own model, and FE. Where they disagree, the agent says which link broke (the model, the drawing or the field) and changes that link, not the others. | A fixed workflow trusts the optimiser's last iterate and finds out at the prototype. A loop can afford three more solves per claim, and it keeps the disagreement as data. | LOP-17, 10 October 05:24: split 7.73's 0.087 × line read 4.1-6.3 as metal or air (`voxel_vs_fe.py`); the cure was the optimiser's formulation, not the drawing |
| **The manufacturing tolerance in the objective.** The design must hold eroded and dilated by the casting's tolerance, so the shape drawn is the shape that works, and the robustness is measured, not assumed. | Robust topology optimisation is known, but rarely run in practice, being three times the solves. An overnight loop pays that as a matter of course. | LOP-17 (`topo_free.py --robust`) |
| **The designer's drawing steps, run as tools.** From an optimised field to a production housing, the steps a designer takes by hand, each a deterministic tool: a smooth envelope fitted over the members, cut by the contract's planes (the split, the end faces), offset inward to the contract's least wall for the pockets' floors, the members' centre-lines as rib paths flush with the envelope, pockets between them. Many readings a night, each judged by FE against the field it came from. | In the published housings the steps after the optimisation are a CAD designer's surface modelling, done once, and the redrawn part is no longer quite the optimised one. A loop can run them as code and keep how much each reading lost. | The engineer's pictures, 2026-10-11 00:03 (a reducer housing's six steps: initial shape, outer surface limit, plane cut, surface offset, new surface, final design); LOP-20 |
| **A pipeline that repairs itself, and learns its cures.** Every step returns a typed failure with its measurement (not watertight, crossing itself, past the factor's ceiling, past the host's memory, a sliver, a loose part); known cures are ladders in code; a coding agent proposes a cure for a new failure, admitted only by the checks and the judges, and the repair is kept as a trajectory. | A fixed workflow stops at its first broken run and waits for a person; a CAE vendor ships fixes by release. A loop can afford to diagnose, cure and re-run in minutes, and its repair records teach tool-using agents what no design dataset holds. | 2026-10-11 night: about 15 failures, each found by a measurement within minutes and now a rule or a rung (`fe.QUALITY_LADDER`, `fe.spread`, `mesh_route.coarse`, `ribbed_cad.union`); [the agents' role](2026-10-11-the-agents-role.md) |
| **The engineer's corrections as data.** Each correction kept with its context and the rule it became; human interventions counted per campaign. | An optimiser or a DOE has no place for "are these three versions really helping?". An agent that turns corrections into rules needs fewer of them, and the records are the data that aligns agents with how engineers work. | 2026-10-11: ten corrections changed the night's course, each now a rule or a default |
| **Every route tried, side by side, at once.** The same field drawn by several routes (organic, meshes, ribbed CAD), each judged, each on the Designs page with its own steps, so the engineer sees where a reading or a route lost and what it gained. | A workflow has one route; trying another is a project. A 5-minute pipeline makes routes into options the agent can try on purpose. | 2026-10-11: flows A, B and C on the same set-up (B and C on one field): 7.97 / 8.03 / 7.33 kg, tilt 0.73 / 0.70 / 1.20 ×, undercut 6 / 1 / 0.2 % |
| **Design variations by asking.** Once the flow is fixed, the optimiser's settings and assumptions are levers (undercuts and cores, the members' thickness, the resolution, several designs of equal merit, how much metal, the objective, the inside, the load cases, the mounts' support, the agent's inputs; [the agents' role](2026-10-11-the-agents-role.md) §9). A user asks in plain language ("lighter, even at some tilt", "what if the mounts were softer?"), and the agent turns the question into variants, runs each in minutes, grades them and says what each lever bought. | A workflow exposes knobs, and the engineer must know which knob answers the question and pay a study for each. The agent maps an intent onto levers, keeps each variant as a hypothesis with its reason and verdict, and reads patterns across them that one run cannot. | The engineer, 2026-10-11 13:31 |
| **Members ranked by a mass sweep.** The optimisation run at several shares of the mass (5 to 40 %), so the load paths that appear first are known as the ones that matter most; a rib grammar draws them first and drops the last ones when mass is short. | One run at one budget says where metal goes, not which of it matters most. A sweep is several runs, an overnight job for a loop. | The engineer's pictures, 2026-10-11 00:03 (a housing's optimisation at 5-40 % mass) |
| **A hand-over whose simplifications are judged before they are given.** The agent reads its field as a designer would (straight rib runs, each one width and height), puts each reading back into the field and judges it by FE, and hands over only the rule that held, with the tests that show it: here, ribs at their median heights lose a third of the stiffness, at their deep heights every line holds for 0.3 kg, the brackets must keep the field's depth. | A designer simplifies by experience and finds out at the CAD's FE, weeks later. Testing six readings of one field is an hour of a loop's runs. | The overnight campaign, 2026-10-13 04:02-04:30 (`reading_field.py`, `final10r`...`final10rd`) |
| **Each line's margin measured against the drawing's own noise.** The same field drawn twice, or judged on two meshes, gives the spread of each line, so a design that passes inside the noise is called a tie, not a pass, and a mode is held with margin. | One FE run reports one number. Knowing which passes are real needs repeated drawings and judgements of one design, which only a loop runs routinely. | `final7` and `final9`: two near-identical fields (the same compliance), a mode 3.2 % clear of an order in one and 2.5 % inside it in the other (2026-10-13 03:41) |
